# API 실패 안내 (공통 에러 상태) — 설계 문서

> **작성일**: 2026-11-03
> **상태**: ✅ 완료

---

## 1. Context (목적)

서버와 `utils/api.ts`까지는 에러가 전달되지만, 호출부 대부분이 catch하지 않아 실패해도 화면에 아무 안내가 없었다.

| 동작 | 기존 동작 |
|---|---|
| 토너먼트 생성 | `console.error`만, 버튼이 다시 켜질 뿐 |
| 라운드 제출 · 취소 | 처리되지 않은 Promise, 버튼 무반응 |
| 다음 회차 시작 | 처리되지 않은 Promise, 버튼 무반응 |

또 `api.ts`는 실패 응답에 무조건 `response.json()`을 호출해, HTML 응답(Vercel 타임아웃 등)이 오면 SyntaxError로 원래 에러가 가려졌다.

## 2. Requirements (요구사항)

- [x] 위 동작이 실패하면 무엇이 실패했고 어떻게 하면 되는지 화면에 표시한다.
- [x] 실패 원인(네트워크 · 400 · 404 · 409 · 500)에 따라 안내 문구를 다르게 한다.
- [x] 500 계열은 서버 내부 메시지를 노출하지 않는다.
- [x] 실패 응답 본문이 JSON이 아니어도 에러 정보(status)를 잃지 않는다.
- [x] 실패한 동작은 로컬 상태를 바꾸지 않는다 (기존 동작 유지).

## 3. 기술 결정

| 방식 | 장점 | 단점 |
|---|---|---|
| 전역 토스트 라이브러리 (react-hot-toast 등) | 여러 개 쌓기 · 자동 닫힘 | 의존성 추가, 현재 화면 수에 비해 과함 |
| React Context 기반 전역 에러 | 어디서든 호출 | 에러가 나는 화면이 2곳뿐이라 과한 추상화 |
| **화면별 `error` 상태 + 공통 `ErrorBanner` + 공통 문구 함수 (채택)** | 의존성 없음, 기존 점수 롤백 구조 재사용 | 화면이 늘면 Context로 옮겨야 할 수 있음 |

## 4. 구조

1. `utils/api.ts` — `request()` 공통 래퍼가 실패를 `ApiError(status, message)`로 던진다. 네트워크 오류는 status 0, JSON이 아닌 본문은 fallback 메시지를 쓴다.
2. `utils/errorMessage.ts` — `toUserMessage(동작, error)`가 status별 문구를 만든다.
3. `useTournament` · 참가자 입력 페이지 — catch에서 `setError(toUserMessage(...))`, 화면 상단 고정 `ErrorBanner`로 표시.

| status | 문구 |
|---|---|
| 0 | {동작}에 실패했습니다. 인터넷 연결을 확인해 주세요. |
| 400 | {동작}에 실패했습니다. {서버 메시지} |
| 404 | {동작}에 실패했습니다. 게임을 찾을 수 없습니다. 링크를 확인해 주세요. |
| 409 | {동작}에 실패했습니다. 이미 처리된 요청입니다. 새로고침해 주세요. |
| 그 외 | {동작}에 실패했습니다. 잠시 후 다시 시도해 주세요. |
